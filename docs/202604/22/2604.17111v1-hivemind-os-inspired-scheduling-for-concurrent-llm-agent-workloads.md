## 摘要
当多个 LLM 编程智能体共享一个受速率限制的 API 端点时，它们表现出的资源争用模式类似于未经调度的操作系统进程竞争 CPU、内存和 I/O。在一个启发性案例中，11 个并行智能体中有 3 个因连接重置和 HTTP 502 错误而终止（失败率为 27%），尽管该 API 具有足够的总容量来按顺序服务所有 11 个智能体。我们提出了 HIVEMIND，这是一个透明的 HTTP 代理，它应用了五种受操作系统启发的调度原语——准入控制、速率限制跟踪、带有熔断机制的 AIMD 背压、Token 预算管理和优先级队列——以消除由无协调并行执行引起的故障模式。该代理无需修改现有的智能体代码，并通过自动检测的提供商配置文件支持 Anthropic、OpenAI 和本地模型 API。我们在七个场景（5-50 个并发智能体）下的评估表明，在资源争用情况下，无协调智能体的失败率为 72-100%，而 HIVEMIND 将失败率降低至 0-18%，并消除了 48-100% 的计算浪费。消融实验表明，透明重试（而非准入控制）是最关键的单一原语，但这些原语在组合使用时效果最佳。针对 Ollama 的真实环境验证确认，HIVEMIND 每次请求增加的代理开销低于 3 毫秒。该系统在 MIT 许可证下开源。

## Abstract
When multiple LLM coding agents share a rate-limited API endpoint, they exhibit resource contention patterns analogous to unscheduled OS processes competing for CPU, memory, and I/O. In a motivating incident, 3 of 11 parallel agents died from connection resets and HTTP 502 errors - a 27% failure rate - despite the API having sufficient aggregate capacity to serve all 11 sequentially. We present HIVEMIND, a transparent HTTP proxy that applies five OS-inspired scheduling primitives - admission control, rate-limit tracking, AIMD backpressure with circuit breaking, token budget management, and priority queuing - to eliminate the failure modes caused by uncoordinated parallel execution. The proxy requires zero modifications to existing agent code and supports Anthropic, OpenAI, and local model APIs via auto-detected provider profiles. Our evaluation across seven scenarios (5-50 concurrent agents) shows that uncoordinated agents fail at 72-100% rates under contention, while HIVEMIND reduces failures to 0-18% and eliminates 48-100% of wasted compute. An ablation study reveals that transparent retry - not admission control - is the single most critical primitive, but the primitives are most effective in combination. Real-world validation against Ollama confirms that HIVEMIND adds under 3ms of proxy overhead per request. The system is open-source under the MIT license.

*   **整体含义**：本文提出了 **HiveMind**，一个受操作系统（OS）启发的调度系统，通过透明代理的方式协调并发智能体的 API 请求，显著提高系统在高负载下的可靠性和资源利用率。

### 2. 方法论
HiveMind 作为一个透明的 HTTP 反向代理，实现了五种核心调度原语：
*   **核心思想**：将 OS 资源管理概念（准入控制、拥塞控制、预算管理）映射到 LLM 智能体领域。
*   **关键技术细节**：
    *   **准入控制（Admission Control）**：使用条件变量（Condition Variables）限制在途请求总数，防止系统过载。
    *   **速率限制跟踪（Rate-limit Tracking）**：结合响应头解析（反应式）和滑动窗口计数器（主动式），监控 RPM（每分钟请求数）和 TPM（每分钟 Token 数）。
    *   **AIMD 背压与熔断（AIMD Backpressure & Circuit Breaking）**：借鉴 TCP 拥塞控制算法，根据延迟和错误率动态调整并发窗口（加性增加/乘性减少）。当错误率超过阈值（如 50%）时触发熔断，快速失败以保护上游服务。
    *   **Token 预算管理**：为每个智能体分配 Token 上限，达到 100% 时强制“检查点”并停止，防止单个智能体耗尽所有配额。
    *   **优先级队列与依赖 DAG**：支持任务优先级排序（Critical 到 Low）和基于最短作业优先（SJF）的调度，同时处理任务间的依赖关系。
    *   **透明重试**：在代理层拦截可重试错误（如 429, 502），通过指数退避和抖动算法自动重试，对智能体代码完全透明。

### 3. 实验设计
*   **实验场景**：设计了 7 个评估场景，包括不同规模的并发（5-50 个智能体）、压力测试、延迟激增测试以及基于真实数据的回放测试（replay-11）。
*   **Benchmark**：对比了“直接执行（Direct）”模式（即无协调的并行执行）。

*   **验证环境**：除了模拟服务器，还使用了 Ollama 和 MLX 等本地模型服务器进行真实环境验证。

*   **性能开销**：实验表明，HiveMind 引入的代理延迟极低，每次请求增加的开销 **< 3ms**。

### 5. 实验数量与充分性
*   **实验规模**：进行了 7 组主要场景实验，涵盖了从低负载到极高负载的梯度。

*   **充分性与客观性**：实验设计较为充分，通过模拟服务器精确控制错误注入率和延迟，保证了实验的可重复性；同时引入本地模型进行真实验证，增强了结果的说服力。

### 6. 主要结论与发现
*   **显著降低失败率**：在 10 个以上智能体并发时，Direct 模式失败率高达 72-100%，而 HiveMind 能将其降至 **0-18%**。
*   **减少资源浪费**：HiveMind 减少了 **48-100%** 因智能体中途崩溃导致的 Token 浪费（在 Opus 级别模型下每天可节省数百美元）。
*   **关键原语发现**：消融实验显示，**“透明重试”是提高智能体存活率最关键的单一原语**，但所有原语组合使用时稳定性最高。
*   **吞吐量优化**：虽然 HiveMind 增加了少量排队时间，但由于避免了智能体崩溃重启，其“有效吞吐量”远高于 Direct 模式。

### 7. 优点
*   **零侵入性**：作为透明代理，无需修改任何现有的智能体代码或框架（如 LangChain）。
*   **理论扎实**：将成熟的操作系统调度理论成功应用于新兴的 LLM 智能体领域，逻辑严密。
*   **多提供商支持**：自动检测并适配 Anthropic、OpenAI、Azure 等不同厂商的速率限制逻辑。
*   **开源贡献**：系统已在 MIT 协议下开源，具有较高的实用价值。

### 8. 不足与局限
*   **单机限制**：目前实现主要针对单机环境，跨多机器共享 API 密钥的分布式调度虽有架构支持但未深入评估。
*   **Token 估算偏差**：在无法获取官方分词器时，使用 4 字符/Token 的启发式估算，对非英语语种可能存在偏差。
*   **缺乏工具层协调**：HiveMind 只管理 API 访问，不处理多个智能体在文件系统或外部工具调用上的冲突（如两个智能体同时修改同一个文件）。
*   **动态优先级不足**：目前的优先级在提交时固定，缺乏根据任务进度动态调整优先级的机制。
