## 摘要
代码智能体正在飞速发展，但对其进行调试也变得日益困难。随着框架在复杂任务中编排并行工具调用和多阶段工作流，智能体的状态转移和错误传播变得难以观察。在这些运行过程中，早期的失误可能会使智能体陷入无意义的循环，甚至级联成根本性错误，形成隐蔽的错误链，从而难以判断智能体何时偏离轨道以及原因。现有的智能体追踪分析要么侧重于简单的交互，要么依赖小规模的人工检查，这限制了它们在实际编程工作流中的可扩展性和实用性。我们提出了 CodeTracer，这是一种追踪架构，它通过不断演进的提取器解析异构运行工件，将完整的状态转移历史重构为具有持久化内存的分层追踪树，并执行故障起始定位，以精准识别故障源头及其下游链条。为了实现系统性评估，我们构建了 CodeTraceBench。该基准测试源自四个广泛使用的代码智能体框架在多种代码任务（如错误修复、重构和终端交互）中生成的大量执行轨迹，并在阶段和步骤层面为故障定位提供监督。实验表明，CodeTracer 的表现显著优于直接提示（direct prompting）和轻量级基准模型，并且在相同预算下，回放其诊断信号能够稳定地恢复原本失败的运行。我们的代码和数据已公开。

## Abstract
Code agents are advancing rapidly, but debugging them is becoming increasingly difficult. As frameworks orchestrate parallel tool calls and multi-stage workflows over complex tasks, making the agent's state transitions and error propagation hard to observe. In these runs, an early misstep can trap the agent in unproductive loops or even cascade into fundamental errors, forming hidden error chains that make it hard to tell when the agent goes off track and why. Existing agent tracing analyses either focus on simple interaction or rely on small-scale manual inspection, which limits their scalability and usefulness for real coding workflows. We present CodeTracer, a tracing architecture that parses heterogeneous run artifacts through evolving extractors, reconstructs the full state transition history as a hierarchical trace tree with persistent memory, and performs failure onset localization to pinpoint the failure origin and its downstream chain. To enable systematic evaluation, we construct CodeTraceBench from a large collection of executed trajectories generated by four widely used code agent frameworks on diverse code tasks (e.g., bug fixing, refactoring, and terminal interaction), with supervision at both the stage and step levels for failure localization. Experiments show that CodeTracer substantially outperforms direct prompting and lightweight baselines, and that replaying its diagnostic signals consistently recovers originally failed runs under matched budgets. Our code and data are publicly available.

### 1. 核心问题与整体含义（研究动机）
随着代码智能体能力的提升，它们执行的任务变得越来越长且复杂（如修复仓库级 Bug）。目前的评估主要关注端到端的成功率（Pass Rate），但当智能体失败时，开发者很难通过杂乱的日志判断：
*   **错误何时开始：** 是环境配置错了，还是最初的逻辑假设就错了？
*   **错误如何传播：** 一个早期的微小失误如何演变成最终的彻底失败？
*   **调试成本高：** 现有的分析依赖人工检查，难以扩展到大规模自动化流程。
**CodeTracer** 的提出是为了将异构的、扁平的执行日志转化为结构化、可追踪的状态转换树，从而实现自动化的故障定位和诊断。

### 2. 方法论：CodeTracer 架构
CodeTracer 将追踪过程分为三个关键阶段：
*   **演进式提取（Evolving Extraction）：** 针对不同智能体框架（如 OpenHands, SWE-Agent）产生的异构日志，系统会自动识别文件布局并适配/合成解析器，将原始记录标准化为包含动作、观察、Diff 和验证结果的“规范步骤”。
*   **树状索引（Tree Indexing）：** 这是核心创新。它将扁平的步骤序列重构为**分层追踪树**。
    *   **探索节点（Exploration）：** 仅查看环境、读文件的操作被归为当前状态下的同级节点。
    *   **状态变更节点（State-changing）：** 修改代码或环境的操作会触发状态转移，生成子节点。
    *   这种结构清晰地展示了智能体是在哪个状态下迷失的。
*   **故障起点定位（Failure Onset Localization）：** 诊断代理遍历追踪树，通过分析验证回归、Diff 大小、回溯频率等特征，定位出导致后续连锁反应的“最早关键错误步骤”（Error Critical Step）。

### 3. 实验设计与基准测试
*   **数据集（CodeTraceBench）：** 作者构建了一个大规模基准测试，包含 4,354 条经过人工标注的执行轨迹。
    *   **来源：** 涵盖 SWE-bench (Verified/Pro), MultiSWE-bench, TerminalBench 等。
    *   **框架：** 使用了 SWE-Agent, MiniSWE-Agent, OpenHands, Terminus 2 四种主流框架。
    *   **模型：** 背后驱动模型包括 GPT-5, Claude-sonnet-4, DeepSeek-V3.2, Qwen3-Coder-480B, Kimi-K2-Instruct。

    *   **CodeTracer：** 完整的提议方法。
*   **评估指标：** 步骤级别的精确率（Precision）、召回率（Recall）和 F1 分数。

*   **实验规模：** 分析了 7,936 条原始轨迹，最终筛选出 3,326 条高质量轨迹进行深入研究。
*   **覆盖面：** 涵盖了 5 种顶级模型和 4 种框架，实验覆盖了从简单的脚本编写到复杂的系统级 Bug 修复。
*   **消融实验：** 专门验证了“演进式提取”和“树状索引”的贡献，证明树状索引对 F1 值的提升贡献最大（约 18.3%）。

### 6. 主要结论与发现
*   **证据-动作鸿沟（Evidence-to-Action Gap）：** 智能体往往能通过探索找到正确的线索，但无法将其转化为正确的修改动作。
*   **成功率饱和点：** 智能体的成功率通常在 40 个迭代步骤左右达到饱和，增加更多步骤往往只会导致无效循环。
*   **错误类型随阶段偏移：** 早期多为环境/依赖错误，后期多为逻辑假设或验证误判。
*   **反思回放（Reflective Replay）：** 将 CodeTracer 的诊断信号反馈给智能体，能显著提升原本失败任务的修复成功率（Pass@1）。

### 7. 优点与亮点
*   **结构化视角：** 将混乱的日志转化为“追踪树”，为智能体研究提供了类似程序员调试代码时的“调用栈”视图。
*   **可扩展性：** 演进式提取器解决了不同框架日志格式不统一的问题，具有很强的工程实用性。
*   **高质量数据：** CodeTraceBench 是目前少有的提供步骤级、过程级标注的代码智能体数据集。

### 8. 不足与局限
*   **标注主观性：** 尽管有指南，但判断哪个步骤是“最早关键错误”仍带有一定的人工主观色彩。
*   **离线限制：** 目前的诊断和回放是在预先收集的轨迹上进行的，尚未完全实现在线实时干预。
*   **模型依赖：** 诊断效果高度依赖于作为“诊断者”的 LLM 本身的能力，如果诊断模型水平不足，可能无法发现深层逻辑错误。
