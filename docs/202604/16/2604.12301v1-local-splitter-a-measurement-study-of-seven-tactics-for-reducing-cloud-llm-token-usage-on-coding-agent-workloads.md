## 摘要
我们针对当小型本地模型可作为前沿云端模型前的分流层时，减少云端大语言模型（LLM）Token 使用量的七种策略进行了系统的测量研究。这七种策略分别是：(1) 本地路由，(2) 提示词压缩，(3) 语义缓存，(4) 本地草拟与云端审核，(5) 最小差异编辑，(6) 结构化意图提取，以及 (7) 结合供应商提示词缓存的批处理。我们在一个开源适配层中实现了所有七种策略，该适配层同时支持 MCP 和兼容 OpenAI 的 HTTP 接口，通过 Ollama 支持任何本地模型，并通过兼容 OpenAI 的端点支持任何云端模型。我们在四类编程智能体工作负载（重编辑型、重解释型、通用对话、重 RAG 型）中，分别对每种策略、策略两两组合以及贪婪累加子集进行了评估。我们测量了节省的 Token 数量、美元成本、延迟和路由准确率。我们的核心发现是，在重编辑型和重解释型工作负载中，T1（本地路由）结合 T2（提示词压缩）可实现 45-79% 的云端 Token 节省；而在重 RAG 型工作负载中，包括 T4（草拟-审核）在内的全套策略可实现 51% 的节省。我们观察到最优策略子集取决于具体的工作负载，我们认为这是对当前部署编程智能体的从业者最具实践指导意义的发现。

## Abstract
We present a systematic measurement study of seven tactics for reducing cloud LLM token usage when a small local model can act as a triage layer in front of a frontier cloud model. The tactics are: (1) local routing, (2) prompt compression, (3) semantic caching, (4) local drafting with cloud review, (5) minimal-diff edits, (6) structured intent extraction, and (7) batching with vendor prompt caching. We implement all seven in an open-source shim that speaks both MCP and the OpenAI-compatible HTTP surface, supporting any local model via Ollama and any cloud model via an OpenAI-compatible endpoint. We evaluate each tactic individually, in pairs, and in a greedy-additive subset across four coding-agent workload classes (edit-heavy, explanation-heavy, general chat, RAG-heavy). We measure tokens saved, dollar cost, latency, and routing accuracy. Our headline finding is that T1 (local routing) combined with T2 (prompt compression) achieves 45-79% cloud token savings on edit-heavy and explanation-heavy workloads, while on RAG-heavy workloads the full tactic set including T4 (draft-review) achieves 51% savings. We observe that the optimal tactic subset is workload-dependent, which we believe is the most actionable finding for practitioners deploying coding agents today.

### 1. 核心问题与整体含义
随着编程智能体（Coding Agents）的普及，调用云端大模型（如 GPT-4, Claude 3.5）的 API 成本已成为开发者和企业的沉重负担。与此同时，1B-7B 参数级的本地小模型（SLM）性能大幅提升。
**研究动机：** 探索如何利用本地小模型作为“分流层（Triage Layer）”，通过多种策略减少发送到云端的 Token 数量，从而在保持响应质量的同时降低运营成本。

### 2. 方法论：七种核心策略
论文提出了一个名为 **Local-Splitter** 的中间件，实现了以下七种正交策略：
*   **T1 - 本地路由 (Local Routing)：** 本地模型判断请求是否“简单”（如重命名、简单解释）。简单请求由本地直接回答，复杂请求才发往云端。
*   **T2 - 提示词压缩 (Prompt Compression)：** 本地模型重写上下文，移除冗余信息，仅保留关键语义、变量名和错误信息。
*   **T3 - 语义缓存 (Semantic Caching)：** 使用向量数据库存储历史请求，对相似度高的重复查询直接返回缓存结果。
*   **T4 - 本地草拟+云端审核 (Drafting with Review)：** 本地模型先生成草稿，云端模型仅负责修改或确认，利用“修改”比“生成”消耗更少输出 Token 的特性。
*   **T5 - 最小差异编辑 (Minimal-diff Edits)：** 针对代码修改任务，仅发送受影响的代码块（Hunks）而非整个文件。
*   **T6 - 结构化意图提取 (Structured Intent Extraction)：** 将冗长的自然语言转换为结构化的 JSON 模板，消除提示词中的修饰性废话。
*   **T7 - 批处理与供应商缓存 (Batching & Vendor Caching)：** 短时间内合并请求，并利用云端厂商提供的提示词缓存功能（如 Anthropic 的 cache_control）。

### 3. 实验设计
*   **工具实现：** 开发了开源适配层，支持 MCP 协议和 OpenAI 兼容接口，后端对接 Ollama（本地）和任意云端 API。

    1.  **WL1 (重编辑型)：** 频繁的代码重构和工具调用。
    2.  **WL2 (重解释型)：** 代码库答疑和逻辑解释。
    3.  **WL3 (混合对话)：** 通用编程聊天。
    4.  **WL4 (重 RAG 型)：** 包含大量检索上下文的长文本任务。

*   **充分性评价：** 实验设计较为系统，涵盖了从单变量到多变量组合的分析，并提供了详细的 Token 节省、成本和延迟数据。

### 6. 主要结论与发现
*   **T1+T2 是黄金组合：** 在编辑和解释型任务中，**本地路由 + 提示词压缩** 表现最佳，可节省 **45%–79%** 的云端 Token。

*   **工作负载依赖性：**

*   **质量权衡：** 使用 T1+T2 组合时，虽然成本大幅下降，但在复杂逻辑上较基准模型有轻微的质量下降。

### 7. 优点
*   **系统性：** 首次在统一基准下对比了七种不同的 Token 优化策略及其相互作用。
*   **实用性：** 提供了开源工具 Local-Splitter，开发者可以直接集成到现有流程中。
*   **分类指导：** 明确指出了不同类型的编程任务应选择不同的策略子集，而非盲目全开。

### 8. 不足与局限
*   **样本量限制：** 每类任务 10 个样本不足以支撑严谨的统计显著性分析。

*   **解析失败：** 在 3B 规模的模型上，T6（结构化提取）经常出现 JSON 解析错误，导致策略失效。
