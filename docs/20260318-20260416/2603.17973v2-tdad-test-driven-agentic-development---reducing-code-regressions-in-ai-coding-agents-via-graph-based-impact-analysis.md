## 摘要
AI 编程智能体能够解决现实世界的软件问题，但它们经常引入回归——即破坏先前通过的测试。目前的基准测试几乎完全集中在解决率上，而对回归行为的研究尚不充分。本文提出了 TDAD（测试驱动的智能体开发），这是一款为 AI 编程智能体执行变更前影响分析的开源工具。TDAD 在源代码和测试之间构建依赖图，以便在提交补丁之前，智能体能够知道需要验证哪些测试并进行自我修正。该图以轻量级智能体技能的形式交付，即智能体在运行时查询的静态文本文件。在 SWE-bench Verified 基准测试中，使用在消费级硬件上运行的两个开源权重模型（Qwen3-Coder 30B，100 个实例；Qwen3.5-35B-A3B，25 个实例）进行评估，TDAD 与原始基线相比，将回归率降低了 70%（从 6.08% 降至 1.82%）。相比之下，在没有针对性测试上下文的情况下添加 TDD 流程指令，反而使回归率增加到 9.94%，甚至差于不采取任何干预措施。当作为智能体技能部署在不同的模型和框架上时，TDAD 将问题解决率从 24% 提高到 32%，证实了提供上下文信息的效果优于规定流程工作流。所有代码、数据和日志均可在 https://github.com/pepealonso95/TDAD 公开获取。

## Abstract
AI coding agents can resolve real-world software issues, yet they frequently introduce regressions -- breaking tests that previously passed. Current benchmarks focus almost exclusively on resolution rate, leaving regression behavior under-studied. This paper presents TDAD (Test-Driven Agentic Development), an open-source tool that performs pre-change impact analysis for AI coding agents. TDAD builds a dependency map between source code and tests so that before committing a patch, the agent knows which tests to verify and can self-correct. The map is delivered as a lightweight agent skill -- a static text file the agent queries at runtime. Evaluated on SWE-bench Verified with two open-weight models running on consumer hardware (Qwen3-Coder 30B, 100 instances; Qwen3.5-35B-A3B, 25 instances), TDAD reduced regressions by 70% (6.08% to 1.82%) compared to a vanilla baseline. In contrast, adding TDD procedural instructions without targeted test context increased regressions to 9.94% -- worse than no intervention at all. When deployed as an agent skill with a different model and framework, TDAD improved issue-resolution rate from 24% to 32%, confirming that surfacing contextual information outperforms prescribing procedural workflows. All code, data, and logs are publicly available at https://github.com/pepealonso95/TDAD.

以下是对该论文的结构化总结：

### 1. 核心问题与整体含义
*   **研究动机**：当前的 AI 编程智能体（如在 SWE-bench 榜单上的模型）虽然在解决新问题上表现出色，但往往会引入**回归（Regressions）**，即导致原本通过的测试失败。
*   **核心矛盾**：现有的评估体系几乎只关注“解决率”（Resolution Rate），而忽视了回归率。在实际工程中，一个引入了回归的补丁通常会被人类维护者拒绝。
*   **挑战**：智能体在大型代码库中难以确定哪些测试与当前修改相关。运行全量测试太慢，而只运行修改文件附近的测试又会遗漏间接依赖。

### 2. 方法论
*   **核心思想**：通过**基于图的影响分析（Graph-Based Impact Analysis）**，在智能体提交补丁前，为其提供精确的“受影响测试列表”，引导其进行自我验证和修正。
*   **关键技术细节**：
    *   **索引阶段（Indexing）**：使用 AST（抽象语法树）解析 Python 仓库，构建包含文件、函数、类和测试用例的依赖图。边类型包括：包含、调用、导入、测试（链接代码与测试）和继承。
    *   **影响分析（Impact Analysis）**：当代码发生变更时，通过四种策略（直接测试、传递调用链、文件覆盖、导入关系）计算测试用例的风险得分，并按优先级排序。
    *   **智能体集成（Skill Integration）**：TDAD 不依赖复杂的 API，而是生成一个轻量级的 `test_map.txt`（可搜索的静态文本）和一个 20 行的指令文件（SKILL.md）。智能体通过 `grep` 查询该文件来确定需要运行的测试。
    *   **自改进循环（Auto-improvement Loop）**：利用外部循环（如 Claude Code）自动迭代 TDAD 自身的代码和提示词，通过基准测试反馈优化工具性能。

### 3. 实验设计
*   **数据集**：**SWE-bench Verified**（包含 500 个经人工验证的 GitHub 真实问题）。
*   **对比方法**：
    1.  **Vanilla**：原始基线，无 TDD 或图信息。
    2.  **TDD Prompt**：仅增加 TDD 流程指令（先写测试再改代码），但不提供图上下文。
    3.  **GraphRAG + TDD (TDAD)**：提供基于图的影响分析上下文。
*   **实验阶段**：
    *   **阶段 1**：100 个实例，使用 Qwen3-Coder 30B 模型，验证回归降低效果。
    *   **阶段 2**：25 个实例，使用 Qwen3.5-35B-A3B 模型和 OpenCode 框架，验证作为“技能”的通用性。

### 4. 资源与算力
*   **硬件**：实验在**消费级硬件**上完成（提到使用了 Apple Silicon 芯片）。
*   **模型部署**：使用 `llama.cpp` 和 `MLX` 框架运行 4-bit 量化模型。
*   **时长**：每个实例限制在 15 分钟内生成补丁。
*   **后端**：默认使用 NetworkX（内存图库），无需 Docker 依赖（早期版本曾使用 Neo4j）。

### 5. 实验数量与充分性
*   **实验规模**：共进行了 28 组实验记录。阶段 1 覆盖了 100 个实例，阶段 2 覆盖了 25 个实例。
*   **充分性**：虽然未覆盖全部 500 个实例（受限于本地算力），但通过消融实验（如 TDD 悖论研究）和自改进循环（15 次迭代）深入探讨了变量影响。实验设计考虑了模型确定性（Temperature=0）和环境隔离（Docker），结果具有客观性。

### 6. 主要结论与发现
*   **大幅降低回归**：TDAD 将测试级回归率从 **6.08% 降低至 1.82%**（降幅达 70%）。
*   **TDD 提示词悖论**：单纯增加 TDD 流程指令而不提供具体的测试上下文，反而使回归率上升至 **9.94%**。这说明对于中小型模型，冗长的流程指令会挤占上下文窗口并分散注意力。
*   **解决率提升**：在阶段 2 中，TDAD 将问题解决率从 24% 提升至 32%，证明了结构化上下文能辅助智能体更好地理解代码库。
*   **上下文胜过流程**：为智能体提供“该检查哪些测试”的信息，比教它“如何做 TDD”更有效。

### 7. 优点
*   **轻量高效**：通过静态文本文件传递知识，避免了复杂的运行时 API 调用或图数据库维护。
*   **实用性强**：显著减少了“灾难性回归”（即破坏所有测试的情况），使 AI 生成的补丁更接近生产环境要求。
*   **自进化能力**：展示了如何利用 AI 智能体自动优化开发工具链。

### 8. 不足与局限
*   **语言限制**：目前仅支持 Python（基于 Python AST 解析）。
*   **静态分析局限**：无法捕获动态分发（Dynamic Dispatch）、猴子补丁（Monkey-patching）或运行时生成的代码。
*   **样本规模**：主要实验基于 100 个样本，虽然趋势明显，但在更大规模或不同语言的仓库上的泛化性仍需进一步验证。
*   **模型依赖**：实验主要针对 30B 级别的本地模型，在顶级闭源模型（如 GPT-4o）上的表现尚未对比。
