## 摘要
仓库级代码智能体在现实世界的功能添加任务中展现出巨大的潜力，这使得对其能力的可靠评估变得日益重要。然而，现有的基准测试主要基于最终测试的正确性将这些智能体视为黑盒进行评估，对于它们如何推理以及故障发生在哪里提供的见解有限。为了解决这一局限性，我们推出了 RACE-bench，这是一个用于评估仓库级功能添加任务中代码智能体的推理增强型基准测试。RACE-bench 包含来自 12 个开源仓库的 528 个真实功能添加实例。每个实例都配有可执行的补丁验证和结构化的中间推理真值（ground truth），涵盖了问题理解、文件定位、实现任务和步骤分解。基于此设计，我们引入了一个双轨评估框架，共同衡量补丁正确性和中间推理质量。我们在 RACE-bench 上评估了三个具有代表性的仓库级代码智能体。在整个基准测试中，不同智能体的解决率（Resolved Rates）在 29% 到 70% 之间。我们的推理层面分析进一步表明，虽然目前的智能体在理解高层意图方面表现良好，但在将意图转化为具体的实现步骤时，其性能会大幅下降。我们还发现，与成功案例相比，应用成功但测试失败的案例表现出更低的推理召回率（下降 35.7%）和更高的过度预测（增加 94.1%）。这些发现强调了通过检查推理过程的质量，在最终补丁正确性之外评估仓库级代码智能体的重要性。

## Abstract
Repository-level code agents have shown strong promise in real-world feature addition tasks, making reliable evaluation of their capabilities increasingly important. However, existing benchmarks primarily evaluate these agents as black boxes based on final test correctness, providing limited insight into how they reason and where failures arise. To address this limitation, we introduce RACE-bench, a reasoning-augmented benchmark for evaluating code agents on repository-level feature addition tasks. RACE-bench contains 528 real-world feature addition instances from 12 open-source repositories. Each instance is paired with executable patch verification and structured intermediate reasoning ground truth covering issue understanding, file localization, implementation tasks, and step decomposition. Based on this design, we introduce a dual-track evaluation framework that jointly measures patch correctness and intermediate reasoning quality. We evaluate three representative repository-level code agents on RACE-bench. On the full benchmark, Resolved Rates range from 29% to 70% across different agents. Our reasoning-level analysis further shows that while current agents perform well at understanding high-level intent, their performance degrades substantially when translating intent into concrete implementation steps. We also find that apply-success but test-fail cases exhibit lower reasoning recall (35.7% decrease) and higher over-prediction (94.1% increase) compared to successful cases. These findings highlight the importance of evaluating repository-level code agents beyond final patch correctness by examining the quality of their reasoning processes.

*   **核心问题**：如何系统地评估代码智能体在处理真实世界功能添加任务时的**中间推理质量**，而不仅仅是最终代码的正确性？

### 2. 方法论：RACE-bench 的构建与评估框架
*   **核心思想**：通过构建包含“推理真值（Reasoning Ground Truth）”的基准测试，实现对智能体从需求理解到代码实现全过程的监控。
*   **关键技术细节**：
    *   **四阶段推理模式**：将推理过程分解为：① **问题理解**（概念解释、目标预期）；② **文件定位**（识别必要代码文件、测试文件）；③ **任务实现**（确定具体的代码实体修改及其目的）；④ **步骤分解**（将实现过程抽象为语义化的任务步骤）。
    *   **基准构建流程**：从 12 个流行 Python 仓库中筛选 PR，经过属性过滤、意图分类（识别功能添加任务）和执行验证（确保 FTP/PTP 测试有效），最终由 LLM 辅助生成推理真值，并经过人工审计。
    *   **双轨评估框架**：
        *   **补丁轨迹**：衡量解决率（Resolved Rate）和补丁应用率。
        *   **推理轨迹**：利用 LLM 作为裁判（LLM-as-Judge），对比智能体交互轨迹与推理真值，计算各模块的**召回率（Recall）**和**过度预测率（Over-prediction）**。

### 3. 实验设计
*   **数据集/场景**：包含 528 个来自 GitHub 真实项目的实例。为了降低成本，还通过难度感知采样构建了包含 100 个实例的 **RACE-bench Lite**。
*   **对比方法（智能体）**：
    *   **AutoCodeRover**：强调结构化导航和局部编辑。
    *   **TraeAgent**：侧重于测试时缩放和迭代改进。
    *   **mini-SWE-Agent**：轻量级、集成执行环境的智能体。
*   **底层模型**：主要使用 DeepSeek V3.2，在 Lite 版本中扩展到了 GLM-4.7 和 GPT-5.2。

### 4. 资源与算力
*   **硬件环境**：实验在一台配备两颗 Intel Xeon Platinum 8358P CPU（共 64 核）和 2 TB RAM 的 Linux 服务器上运行。
*   **算力细节**：论文未提及具体的 GPU 型号，因为主要通过官方 API 调用 LLM。实验重点记录了**Token 消耗**和**执行时间**（DeepSeek 响应最慢，GPT-5.2 在交互效率和 Token 节省上表现最优）。

### 5. 实验数量与充分性
*   **实验规模**：在全量 528 个实例上测试了 3 种智能体，在 Lite 子集上进行了跨模型的交叉验证。
*   **充分性与公平性**：
    *   **客观性**：使用了 Docker 容器化环境确保环境一致性。
    *   **公平性**：所有智能体均使用默认配置，且温度设为 0 以保证可重复性。
    *   **验证**：对推理真值进行了 LLM 审计和人工抽检（一致性达 96%），证明了基准数据的可靠性。

### 6. 主要结论与发现
*   **性能分化**：不同智能体解决率差异巨大（29% - 70%），mini-SWE-Agent 表现最佳。
*   **推理瀑布式退化**：智能体在高层意图理解上表现极佳（得分 > 9.2/10），但在转化为具体文件定位、任务识别和步骤分解时，性能逐级下降。**步骤分解是当前最核心的瓶颈**。
*   **失败特征**：应用成功但测试失败的案例，通常伴随着召回率的大幅下降（-35.7%）和严重的过度预测（+94.1%，即做了很多无关修改）。
*   **模型与架构的关系**：底层 LLM 的能力受限于智能体架构。优秀的架构（如 mini-SWE-Agent）能更稳定地发挥不同模型的能力。

### 7. 优点
*   **细粒度诊断**：首次为仓库级功能添加任务提供了结构化的推理评估，能够定位智能体在哪个环节“掉链子”。
*   **真实性高**：数据源于真实的 GitHub PR，且包含复杂的跨文件修改场景。
*   **评估维度全面**：不仅看结果，还看过程中的冗余度（过度预测）和准确度。

### 8. 不足与局限
*   **语言局限**：目前仅覆盖 Python 语言仓库。
*   **LLM 裁判偏差**：虽然使用了混合匹配策略，但语义评估仍部分依赖 LLM-as-Judge，可能存在潜在偏见。
*   **推理提取难度**：不同智能体的日志格式不一，将非结构化轨迹映射到统一推理模块时可能存在信息丢失。
*   **单次尝试限制**：实验基于单次尝试（Pass@1），未探讨多次迭代或采样对推理质量的影响。
