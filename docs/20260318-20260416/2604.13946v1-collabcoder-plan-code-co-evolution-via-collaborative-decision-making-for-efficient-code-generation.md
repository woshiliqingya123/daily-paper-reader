## 摘要
自动化代码生成仍然是软件工程中一个长期存在的挑战，因为传统的多智能体框架往往受限于静态规划、孤立执行、高计算开销以及对复杂任务的适应性有限。本文介绍了 CollabCoder，这是一种新颖的计划-代码协同演化框架，通过动态多智能体协作来提升代码生成质量。其核心思想是在计划模块和代码模块之间设计一种协作决策机制，以确定在调试过程中应当执行哪个模块。在广泛使用的基准测试上进行的实验表明，CollabCoder 在不同任务中均能持续提高代码质量和鲁棒性。重要的是，CollabCoder 在降低计算开销的同时，达到了与当前最先进方法相当甚至更优的性能，且随着基准测试难度的增加，其效率优势愈发显著。在更具挑战性的 LiveCodeBench 和 xCodeEval 基准测试中，我们的方法相较于强基线模型性能提升了 11-20%，同时每次执行平均减少了 4-10 次 API 调用。

## Abstract
Automated code generation remains a persistent challenge in software engineering, as conventional multi-agent frameworks are often constrained by static planning, isolated execution, high computational overhead, and limited adaptability to complex tasks. This paper introduces CollabCoder, a novel Plan-Code Co-Evolution framework that improves code generation through dynamic multi-agent collaboration. The core idea is to design a collaborative decision-making process between the plan module and the code module to decide which module should be executed for the debugging process. Extensive experiments on widely used benchmarks demonstrate that CollabCoder consistently improves code quality and robustness across tasks. Importantly, CollabCoder achieves performance comparable to or exceeding current state-of-the-art methods while reducing computational overhead, with efficiency gains becoming more pronounced as benchmark difficulty increases. On the more challenging LiveCodeBench and xCodeEval benchmarks, our approach improves performance by 11-20% over strong baselines while reducing the number of API calls by an average of 4-10 per execution.

传统的 LLM 代码生成框架（如“先计划后代码”模式）存在两个核心局限：
*   **静态规划的僵化性：** 规划模块在生成初始计划后通常保持固定，即使后续代码调试证明计划本身存在逻辑错误，系统也只会反复修改代码，导致陷入局部最优或无效循环。
*   **高昂的计算开销：** 现有的多智能体框架（如 MapCoder）往往采用复杂的迭代路径，导致 API 调用次数和 Token 消耗巨大，且在处理复杂竞赛级题目时效率低下。

**CollabCoder 的核心意义**在于提出了一种“计划-代码协同演化”机制，让智能体能够动态决定是该修改“解题思路（计划）”还是“具体实现（代码）”，从而实现更高效、更精准的代码生成。

### 2. 方法论：核心思想与技术细节
CollabCoder 由三个核心智能体组成：规划智能体 ($A_{plan}$)、代码智能体 ($A_{code}$) 和调试智能体 ($A_{debug}$)。其核心创新在于调试智能体内部的两个模块：

*   **协作决策模块 (CDM)：**
    *   **多维度分析：** 在每次迭代中，CDM 从三个维度进行诊断：计划级分析（算法逻辑是否正确）、代码级分析（实现是否有 Bug）以及计划-代码对齐分析（代码是否忠实执行了计划）。
    *   **共识决策：** 通过一个共识函数 $F_{cons}$，结合预设的信任权重（计划、代码、对齐权重分别为 0.4, 0.3, 0.3），计算得分以决定下一步是更新计划 ($D=0$) 还是更新代码 ($D=1$)。
*   **推理轨迹模块 (RT)：**
    *   **状态化调试：** 不同于以往“无状态”的调试，RT 模块会维护一个持久的调试策略状态 $R^{(t)}$。它记录历史错误模式和修正尝试，避免在后续迭代中重复无效的修改，实现“从错误中学习”。
*   **算法流程：**
    1. 生成初始计划和代码。
    2. 执行测试用例，若失败则进入 CDM。
    3. CDM 分析失败原因并决定更新目标（计划或代码）。
    4. RT 模块根据分析结果更新调试策略。
    5. 根据决策调用 $A_{plan}$ 或 $A_{code}$ 进行针对性修复，进入下一轮迭代。
