## 摘要
仓库级代码智能任务要求大语言模型（LLM）处理长且包含多个文件的上下文。此类输入带来了三个挑战：关键上下文可能被噪声掩盖、因窗口限制而被截断，以及推理延迟增加。上下文压缩通过压缩输入来缓解这些风险。虽然在自然语言处理（NLP）领域已有研究，但其在代码任务中的适用性在很大程度上仍未得到探索。我们提出了首个针对仓库级代码智能的上下文压缩系统性实证研究，将八种方法归纳为三种范式：离散 Token 序列、连续潜向量和视觉 Token。我们在代码补全和生成任务上对这些方法进行了评估，并测量了其性能和效率。结果表明上下文压缩是有效的：在 4 倍压缩率下，连续潜向量方法的 BLEU 分数比全上下文性能高出多达 28.3%，这表明它们过滤了噪声而不仅仅是进行了截断。在效率方面，所有范式都降低了推理成本。在高压缩率下，视觉和基于文本的压缩都能实现高达 50% 的端到端延迟降低，接近于不使用仓库上下文的推理成本。这些发现确立了上下文压缩作为一种可行的方法，并为范式选择提供了指导。

## Abstract
Repository-level code intelligence tasks require large language models (LLMs) to process long, multi-file contexts. Such inputs introduce three challenges: crucial context can be obscured by noise, truncated due to limited windows, and increased inference latency. Context compression mitigates these risks by condensing inputs. While studied in NLP, its applicability to code tasks remains largely unexplored. We present the first systematic empirical study of context compression for repository-level code intelligence, organizing eight methods into three paradigms: discrete token sequences, continuous latent vectors, and visual tokens. We evaluate them on code completion and generation, measuring performance and efficiency. Results show context compression is effective: at 4x compression, continuous latent vector methods surpass full-context performance by up to 28.3% in BLEU score, indicating they filter noise rather than just truncating. On efficiency, all paradigms reduce inference cost. Both visual and text-based compression achieve up to 50% reduction in end-to-end latency at high ratios, approaching the cost of inference without repository context. These findings establish context compression as a viable approach and provide guidance for paradigm selection.

### 1. 核心问题与整体含义（研究动机和背景）
在处理仓库级代码任务（如跨文件代码补全、项目感知代码生成）时，大语言模型（LLM）需要处理跨越多个文件的长上下文。这带来了三大挑战：
*   **噪声干扰：** 关键信息常被大量无关代码（如样板代码、冗余声明）掩盖，导致“迷失在中间（Lost in the Middle）”现象。
*   **窗口限制：** 庞大的代码库往往超出模型的上下文窗口上限，导致强制截断。
*   **推理开销：** 自注意力机制的平方复杂度导致推理延迟和显存消耗随长度剧增。
虽然上下文压缩在NLP领域已有研究，但在代码领域的有效性尚不明确。本文旨在探究压缩技术能否在降低开销的同时，通过过滤噪声提升代码LLM的性能。

### 2. 核心方法论
论文将现有的上下文压缩方法归纳为三种范式，并构建了一个统一的评估框架：
*   **文本到文本 (Text-to-Text, T2T)：** 在离散 Token 空间操作。通过计算 Token 或代码段的重要性分数（如困惑度 Perplexity），过滤掉低信息量的部分。代表方法包括 LLMLingua 系列。
*   **文本到向量 (Text-to-Vector, T2V)：** 将上下文编码为连续的潜向量（Memory Tokens）。核心思想是训练一个轻量级编码器，将长文本压缩为固定数量的向量，而冻结下游 LLM 解码器。论文细分了四种变体，涉及不同的内存组织（局部 vs. 传播）和提取机制（自注意力聚合 vs. 查询驱动提取）。
*   **文本到图像 (Text-to-Image, T2I)：** 利用多模态模型（VLM）的高信息密度。将代码渲染为高分辨率图像，再由视觉编码器转化为视觉 Token。压缩率通过调整图像分辨率来控制。

### 3. 实验设计
*   **数据集与任务：** 使用 **ComplexCodeEval** 评测集，涵盖 Python 和 Java 两种语言。任务包括**代码生成**（从注释/签名生成函数体）和**代码补全**（预测缺失的代码片段）。
*   **模型：** 选用 Qwen2.5 系列。T2V 和 T2T 使用 Qwen2.5-Coder (3B/7B)；T2I 使用 Qwen2.5-VL (3B/7B)。
*   **对比基准 (Benchmark)：** 
    *   **Full Context：** 直接输入未压缩的完整上下文（性能上限）。
    *   **No Context：** 仅提供任务指令，不提供任何仓库上下文（性能下限）。
    *   **压缩方法：** 对比了 8 种代表性方法（T2T 3种，T2V 4种变体，T2I 1种）。
*   **评估指标：** BLEU、编辑相似度 (ES) 和精确匹配 (EM)。

### 4. 资源与算力
*   **硬件设施：** 实验在一台配备 **8 台 NVIDIA A100 80GB GPU** 的服务器上运行。
*   **训练细节：** 
    *   T2V 范式需要训练：首先在 StarCoderData（20万个样本）上进行预训练（3个 epoch），然后在 ComplexCodeEval 训练集上进行下游适配（3个 epoch）。
    *   训练使用 BF16 混合精度，序列长度为 16,384。
    *   每个训练或推理任务在单张 GPU 上运行。

### 5. 实验数量与充分性
*   **实验规模：** 论文在 2 种语言、2 种任务、2 种模型规模（3B/7B）以及多个压缩比（2x 到 128x）下进行了详尽测试。
*   **充分性：** 实验设计非常全面，不仅对比了任务性能，还深入分析了推理延迟、显存占用以及文本恢复能力（Text Recovery）。
*   **客观性：** 通过设置“无上下文”和“全上下文”两个极端基准，客观地展示了压缩技术在不同压缩比下的收益与损失。

### 6. 主要结论与发现
*   **T2V 表现最优（超越全上下文）：** 在 4 倍压缩下，T2V 在 Python 补全任务上的 BLEU 分数比全上下文高出 **28.3%**。这证明了潜向量压缩能有效过滤仓库噪声，强化任务相关信号。
*   **T2I 任务不对称：** T2I 在代码补全上表现尚可，但在代码生成上性能骤降（下降约 50%）。原因是均匀渲染图像会导致跨文件依赖等细粒度逻辑信号丢失。
*   **T2T 存在临界点：** 基于困惑度的 T2T 压缩在 7x-12x 压缩比时性能会坍缩至“无上下文”水平，且对 Python 的缩进结构非常敏感。
*   **效率提升显著：** 所有范式均能降低延迟。T2I 在高压缩比下延迟降低最明显（约 50%），而 T2V 的开销最为稳定且可预测。

### 7. 优点与亮点
*   **首次系统性研究：** 填补了代码领域长上下文压缩研究的空白。
*   **发现“超性能”现象：** 揭示了压缩不仅是为了效率，合理的压缩（T2V）甚至能通过去噪提升模型对代码逻辑的理解。
*   **部署导向：** 提供了详细的效率分析（延迟、显存），为实际工业部署提供了范式选择指南。

### 8. 不足与局限
*   **T2V 的训练成本：** T2V 虽然性能最好，但需要针对特定模型进行预训练和适配，不如 T2T 那样开箱即用。
*   **代码结构的敏感性：** 现有的压缩方法（尤其是 T2T 和 T2I）对代码特有的语法结构（如缩进、导入语句）缺乏显式保护，容易在激进压缩时破坏程序逻辑。
*   **语言覆盖：** 虽然测试了 Python 和 Java，但对于 C++ 或 Rust 等具有更复杂内存管理或宏系统的语言，压缩的效果尚待验证。
