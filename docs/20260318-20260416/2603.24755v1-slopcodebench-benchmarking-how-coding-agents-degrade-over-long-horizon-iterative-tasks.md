## 摘要
软件开发是迭代式的，然而编程智能体基准测试绝大多数是在完整规范下评估单次生成的解决方案。代码虽然能通过测试套件，但会变得越来越难以扩展。最近的迭代基准测试试图弥补这一差距，但对智能体的设计决策限制过于严格，无法真实衡量代码质量如何影响未来的扩展。我们推出了 SlopCodeBench，这是一个与语言无关的基准测试，包含 20 个问题和 93 个检查点。在该基准测试中，智能体在不断演进的规范下重复扩展其先前的解决方案，这些规范强制要求做出架构决策，但不规定内部结构。我们追踪了两个轨迹级的质量信号：冗余度（verbosity，即冗余或重复代码的比例）和结构侵蚀（structural erosion，即集中在高复杂度函数中的复杂度份额）。在 11 个模型中，没有智能体能端到端地解决任何问题；最高检查点解决率为 17.2%。质量稳步下降：在 80% 的轨迹中结构侵蚀有所增加，在 89.8% 的轨迹中冗余度有所增加。与 48 个开源 Python 仓库相比，智能体生成的代码冗余度高出 2.2 倍，且结构侵蚀明显更严重。对其中 20 个仓库的长期追踪显示，人类编写的代码质量保持平稳，而智能体代码随每次迭代而恶化。提示词干预研究表明，初始质量可以得到改善，但这并不能阻止退化。这些结果表明，基于通过率的基准测试系统性地低估了扩展鲁棒性，且当前的智能体缺乏迭代软件开发所要求的设计纪律。

## Abstract
Software development is iterative, yet agentic coding benchmarks overwhelmingly evaluate single-shot solutions against complete specifications. Code can pass the test suite but become progressively harder to extend. Recent iterative benchmarks attempt to close this gap, but constrain the agent's design decisions too tightly to faithfully measure how code quality shapes future extensions. We introduce SlopCodeBench, a language-agnostic benchmark comprising 20 problems and 93 checkpoints, in which agents repeatedly extend their own prior solutions under evolving specifications that force architectural decisions without prescribing internal structure. We track two trajectory-level quality signals: verbosity, the fraction of redundant or duplicated code, and structural erosion, the share of complexity mass concentrated in high-complexity functions. No agent solves any problem end-to-end across 11 models; the highest checkpoint solve rate is 17.2%. Quality degrades steadily: erosion rises in 80% of trajectories and verbosity in 89.8%. Against 48 open-source Python repositories, agent code is 2.2x more verbose and markedly more eroded. Tracking 20 of those repositories over time shows that human code stays flat, while agent code deteriorates with each iteration. A prompt-intervention study shows that initial quality can be improved, but it does not halt degradation. These results demonstrate that pass-rate benchmarks systematically undermeasure extension robustness, and that current agents lack the design discipline iterative software development demands.

### SlopCodeBench：编程智能体长程迭代退化基准测试论文总结

#### 1. 核心问题与整体含义（研究动机和背景）
传统的编程智能体基准测试（如 SWE-bench）大多侧重于“单次生成”（Single-shot），即根据完整的规范一次性生成代码。然而，现实中的软件开发是**迭代式**的：开发者必须在现有代码基础上不断扩展新功能。
*   **研究动机**：现有的评估忽略了代码的“可扩展性”和“长期维护性”。智能体生成的代码可能通过当前的单元测试，但往往包含大量冗余、缺乏设计的代码（俗称“Slop”），导致后续迭代难度剧增。
*   **核心问题**：当编程智能体被迫在自己编写的、可能存在设计缺陷的代码基础上进行多次扩展时，其性能和代码质量会如何演化？

#### 2. 方法论：核心思想与关键技术
论文提出了 **SlopCodeBench (SCBench)**，其核心思想是模拟真实的软件演进过程。
*   **迭代机制**：每个任务包含多个检查点（Checkpoint）。智能体在 $C_i$ 阶段必须基于自己在 $C_{i-1}$ 阶段生成的代码进行修改和扩展。
*   **设计原则**：
    *   **无预设接口**：只规定外部 CLI 或 API 行为，不规定内部函数签名，强制智能体自行做架构决策。
    *   **隐藏测试集**：智能体看不到测试用例，必须根据自然语言规范推断边界情况。
    *   **语言无关**：任务定义为黑盒契约，理论上支持任何编程语言（本文重点实验了 Python）。
*   **质量度量指标**：
    *   **结构侵蚀 (Structural Erosion)**：衡量复杂度是否过度集中。定义为高复杂度函数（循环复杂度 CC > 10）所占的“复杂度质量”比例。公式结合了循环复杂度和代码行数的平方根。
    *   **冗余度 (Verbosity)**：利用 137 条 AST-Grep 规则检测无效代码模式（如单次使用的变量、无意义的包装函数）以及代码克隆比例。

#### 3. 实验设计
*   **数据集/场景**：包含 20 个复杂的编程问题，共 93 个检查点。涵盖了图算法、DSL 解释器、REST API、数据库迁移工具等。
*   **对比方法**：评估了 11 个主流模型，包括 Anthropic 的 Claude 系列（3.5/3.6/4.5/4.6）、OpenAI 的 GPT-5/Codex 系列以及 GLM。
*   **校准基准**：引入了 48 个维护良好的开源 Python 仓库（如 Scikit-learn, Django, FastAPI 等）作为人类基准，并追踪了其中 20 个仓库的历史提交记录以对比演化轨迹。
*   **提示词策略**：对比了“直接解决”（Just-solve）、“反冗余”（Anti-slop）和“计划优先”（Plan-first）三种提示词干预手段。

#### 4. 资源与算力
*   **算力说明**：论文未详细列出具体的 GPU 训练算力（因为主要评估推理能力），但详细记录了推理成本。
*   **推理开销**：每个检查点设置了 2 小时的墙钟时间限制。实验显示，随着任务推进，推理成本显著上升。例如，GPT-5.4 在某些任务上的总成本超过 300 美元，单次检查点最高花费可达 15 美元。

#### 5. 实验数量与充分性
*   **实验规模**：共进行了 25 种不同的配置运行（模型 + Harness 版本），覆盖了 930 个智能体生成的检查点。
*   **充分性**：实验设计非常全面。不仅对比了不同厂商的模型，还通过人类仓库进行了横向校准，并对提示词策略进行了消融研究。通过引入“隔离通过率”（Iso.）和“回归通过率”来区分新功能实现与旧功能破坏，实验逻辑严密且客观。

#### 6. 主要结论与发现
*   **全流程失败**：在所有 11 个模型中，**没有一个智能体能端到端地解决任何一个完整问题**。最高检查点解决率仅为 17.2%。
*   **质量持续退化**：随着迭代进行，80% 的任务轨迹出现了结构侵蚀加剧，89.8% 的轨迹出现了冗余度上升。
*   **人机差距巨大**：智能体生成的代码冗余度是人类开发者的 2.2 倍。更重要的是，人类代码质量随时间趋于平稳，而智能体代码随迭代呈线性恶化。
*   **提示词并非万灵药**：虽然“反冗余”提示词能改善初始代码质量（降低截距），但无法改变随迭代退化的速率（斜率）。

#### 7. 优点
*   **填补评估空白**：首次系统性地量化了智能体在长程迭代任务中的“架构腐化”现象。
*   **真实性高**：强制智能体“自食其果”（继承自己的设计决策），比使用黄金代码重置的基准测试更接近真实开发。
*   **度量科学**：引入的结构侵蚀和冗余度指标为评估 LLM 生成代码的“健康度”提供了有力工具。

#### 8. 不足与局限
*   **语言覆盖**：虽然设计上支持多语言，但目前的实验数据主要集中在 Python 轨道。
*   **成本限制**：由于任务长且成本高，很难进行大规模的重复采样（如 Pass@k），可能存在一定的随机性偏差。
*   **Harness 依赖**：实验结果在一定程度上受到智能体框架（如 Claude Code 或 Codex CLI）实现细节的影响，尽管作者尝试通过版本敏感性分析来缓解这一问题。
