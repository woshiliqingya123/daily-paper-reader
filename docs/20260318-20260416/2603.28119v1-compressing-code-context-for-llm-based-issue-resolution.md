## 摘要
大语言模型（LLMs）目前已具备解决真实 GitHub 问题的能力。然而，现有方法往往过度近似代码上下文，并面临两个复合问题：处理海量输入的高昂成本，以及由于噪声充斥上下文窗口并干扰模型捕捉 Bug 修复信号而导致的低效。现有的压缩技术未能解决这一矛盾：通用压缩器会损害代码的语义完整性，而特定于代码的工具则缺乏对代码结构和任务上下文的感知，无法保留关键的补丁要素。针对这一问题，我们提出了一个包含两个组件的新型框架。首先是 Oracle 引导的代码蒸馏（OCD），这是一种结合了遗传搜索和增量调试（Delta Debugging）的上下文蒸馏算法，能够系统地将代码上下文缩减为最小充分子序列，仅保留成功修复所需的要素。我们利用这些蒸馏数据微调了 SWEzze，这是一个轻量级模型，能够在推理阶段学习压缩代码上下文，在过滤噪声和对抗干扰的同时保留修复要素。在 SWE-bench Verified 基准测试中，针对三种前沿 LLM 的评估结果显示，SWEzze 在不同模型上保持了约 6 倍的稳定压缩率，相对于未压缩设置减少了 51.8%-71.3% 的总 Token 预算，将问题修复率提高了 5.0%-9.2%，并且与最先进的上下文压缩基准相比，在有效性、压缩比和延迟之间实现了最佳的整体平衡。

## Abstract
Large Language Models (LLMs) are now capable of resolving real-world GitHub issues. However, current approaches overapproximate the code context and suffer from two compounding problems: the prohibitive cost of processing massive inputs, and low effectiveness as noise floods the context window and distracts the model from the bug-fixing signal. Existing compression techniques fail to resolve this tension: generic compressors compromise the semantic integrity of code, while code-specific tools lack awareness of code structure and task context to preserve essential patch ingredients. To address this, we propose a novel framework consisting of two components. First, Oracle-guided Code Distillation (OCD), a context distillation algorithm that combines genetic search and delta debugging to systematically reduce code contexts to their minimal sufficient subsequence - retaining only the ingredients required for a successful fix. We use this distilled data to fine-tune SWEzze, a lightweight model that learns to compress code context at inference time, filtering noise and combating distraction while preserving fix ingredients. Evaluated on SWE-bench Verified across three frontier LLMs, SWEzze maintains a stable compression rate of about 6 times across models, reduces the total token budget by 51.8%-71.3% relative to the uncompressed setting, improves issue resolution rates by 5.0%-9.2%, and delivers the best overall balance among effectiveness, compression ratio, and latency compared with state-of-the-art context compression baselines.

### 1. 核心问题与研究动机
*   **核心问题**：LLM 在处理仓库级代码任务时，通常需要依赖大量的上下文（定义、调用链等）。现有的检索方法（如 RAG）往往会引入过量的无关代码（上下文过度近似），导致两个问题：
    1.  **高昂成本**：推理成本随 Token 数量线性或二次方增长。
    2.  **模型分心**：无关代码（噪声）会干扰模型捕捉关键的“修复信号”，降低修复成功率。
*   **研究动机**：现有的压缩技术（如 LLMLingua）要么破坏代码语义完整性，要么仅基于词法相似度而忽略了修复所需的关键要素（Fix Ingredients）。

### 2. 方法论
该框架由两个核心阶段组成：**Oracle 引导的代码蒸馏 (OCD)** 和 **SWEzze 压缩模型**。

*   **Oracle 引导的代码蒸馏 (OCD)**：
    *   **目标**：寻找“最小充分上下文”（Minimal Sufficient Context, MSC），即能让 LLM 成功修复 Bug 的最小代码子序列。
    *   **两阶段搜索**：
        1.  **遗传算法 (GA)**：在指数级的代码组合空间中搜索能够使补丁通过测试的配置。
        2.  **分层增量调试 (HDD)**：在文件、函数、块三个层级上系统性地移除冗余单元，确保最终保留的每一行代码都是功能性必需的。
    *   **优先级引导**：利用测试覆盖率、补丁重叠度和符号重叠度为代码单元打分，引导搜索过程。
*   **SWEzze 压缩模型**：
    *   **模型架构**：基于 `Qwen3-Reranker-0.6B` 的轻量级交叉编码器（Cross-encoder）。
    *   **训练策略**：使用 OCD 产生的数据进行微调。采用 **LoRA** 参数高效微调技术，并引入**角色感知样本加权**（如 Schema 定义权重大于通用工具类），解决正负样本极度不平衡的问题。
    *   **推理流程**：在推理时，SWEzze 对候选代码段进行评分，并根据预设的 Token 预算进行贪心选择，无需访问 Oracle。

### 3. 实验设计
*   **数据集**：
    *   **训练集**：基于 `SWE-Smith` 抽取的 10,000 个问题，通过 OCD 蒸馏出 3,157 个有效实例。
    *   **测试集**：`SWE-bench Verified`（500 个真实的 GitHub 问题）。
*   **下游修复模型**：使用了三种前沿 LLM：`GPT-5.2`、`DeepSeek-V3.2` 和 `Qwen3-Coder-Next`。

*   **模型规模**：SWEzze 基于 0.6B 参数的小模型，适合在商用 GPU 上运行。

### 5. 实验数量与充分性
*   **实验规模**：在 500 个真实问题上进行了端到端测试，涵盖了 12 个主流 Python 仓库。
*   **多模型验证**：在三种不同架构、不同厂商的 LLM 上均验证了有效性，证明了压缩结果的泛化性。
*   **消融与分析**：

### 6. 主要结论与发现
*   **性能提升**：SWEzze 将问题解决率提高了 **5.0%–9.2%**（相比不压缩），证明了“去噪”比“全量信息”更有利于 LLM 修复 Bug。
*   **高效压缩**：实现了约 **6 倍** 的稳定压缩率，减少了 **51.8%–71.3%** 的总 Token 消耗。
*   **覆盖度**：SWEzze 覆盖了 93.8%–99.2% 的可解决案例，表现出极强的鲁棒性。
*   **关键发现**：对于仓库级任务，保留“修复要素”（如类型定义、调用链）比单纯追求高压缩比或文本相似度更重要。

### 7. 优点
*   **任务感知性强**：通过 OCD 算法直接以“能否修复成功”作为金标准，捕捉到了传统启发式方法无法识别的深层语义依赖。
*   **结构保护**：采用分层（文件-函数-块）压缩策略，并使用占位符（如 `# ... lines omitted`），维持了代码的语法骨架。
*   **模型无关性**：虽然训练数据由一种模型生成，但在其他不同厂商的模型上表现一致，具有良好的迁移性。

### 8. 不足与局限
*   **训练成本**：OCD 过程需要频繁调用 LLM 和运行测试套件，数据构造阶段的算力/金钱开销较大。
*   **分布偏移**：训练时使用了 Oracle 信息（如 ground-truth 补丁），而推理时仅靠问题描述，这种信息差可能导致模型在极复杂场景下评分失准。
*   **语义歧义处理**：在处理具有相同签名但逻辑不同的重写函数时，0.6B 的小模型可能难以进行极精细的语义区分。
