## 摘要
基于大语言模型（LLM）的代码智能体通常将代码库视为非结构化文本，通过脆弱的字符串匹配来应用编辑，而这种方式经常因格式偏移或歧义模式而失败。我们提出将代码库重新构架为一个结构化动作空间，使智能体在命名的抽象语法树（AST）实体上而非文本片段上进行操作。我们的框架 CODESTRUCT 提供了用于检索完整语法单元的 readCode，以及用于对语义程序元素应用经过语法验证的转换的 editCode。在 SWE-Bench Verified 基准测试中，针对六种 LLM 的评估显示，CODESTRUCT 将 Pass@1 准确率提高了 1.2-5.0%，同时为大多数模型减少了 12-38% 的 token 消耗。在基于文本的界面下经常无法生成有效补丁（patch）的模型受益最为显著：GPT-5-nano 的性能提升了 20.8%，其空补丁失败率从 46.6% 降至 7.2%。在 CodeAssistBench 上，我们观察到一致的准确率提升（+0.8-4.4%）以及高达 33% 的成本降低。研究结果表明，结构感知界面为代码智能体提供了更可靠的基础。

## Abstract
LLM-based code agents treat repositories as unstructured text, applying edits through brittle string matching that frequently fails due to formatting drift or ambiguous patterns. We propose reframing the codebase as a structured action space where agents operate on named AST entities rather than text spans. Our framework, CODESTRUCT, provides readCode for retrieving complete syntactic units and editCode for applying syntax-validated transformations to semantic program elements. Evaluated on SWE-Bench Verified across six LLMs, CODESTRUCT improves Pass@1 accuracy by 1.2-5.0% while reducing token consumption by 12-38% for most models. Models that frequently fail to produce valid patches under text-based interfaces benefit most: GPT-5-nano improves by 20.8% as empty-patch failures drop from 46.6% to 7.2%. On CodeAssistBench, we observe consistent accuracy gains (+0.8-4.4%) with cost reductions up to 33%. Our results show that structure-aware interfaces offer a more reliable foundation for code agents.

### 1. 核心问题与整体含义（研究动机和背景）
传统的 LLM 代码智能体（Code Agents）在处理代码库时存在**抽象失配**问题：它们将程序视为扁平的“非结构化文本”，通过行号或字符串匹配来定位和编辑代码。这种方式极其脆弱，容易受到格式微调（如空格、缩进）的影响，导致“找不到匹配项”或“匹配歧义”等错误。此外，文本驱动的编辑往往要求模型重复生成大量未修改的代码，造成 Token 浪费。
**研究动机**：将代码库重新定义为**结构化动作空间**，让智能体直接操作命名的 AST（抽象语法树）实体（如类、函数、方法），从而提高代码处理的鲁棒性、精确度和效率。

### 2. 方法论：核心思想与关键技术
CODESTRUCT 框架的核心思想是利用 AST 将代码库转化为可编程的动作空间，提供两个结构感知原语：
*   **`readCode`（结构化检索）**：
    *   **目录浏览**：返回文件列表。
    *   **文件摘要**：对于大文件，仅返回类和函数的签名（Signature），避免上下文过载。
    *   **实体检索**：通过选择器（Selector，如 `file.py::ClassName::method`）精确提取完整的语法单元，确保代码不被截断。
*   **`editCode`（结构化编辑）**：
    *   **原子操作**：支持 `insert`（插入）、`replace`（替换）和 `removal`（删除）。
    *   **语法验证**：在应用修改前，工具会自动验证修改后的 AST 是否符合语法规范，拒绝产生语法错误的补丁。
    *   **格式保持**：自动处理缩进和上下文对齐，智能体只需提供新的逻辑内容，无需重复生成周围代码。

### 7. 优点
*   **范式创新**：将代码编辑从“文本处理”提升到了“语义操作”，符合人类开发者的思维模式。
*   **通用性强**：通过 Model Context Protocol (MCP) 实现，可以无缝集成到现有的智能体框架（如 OpenHands）中。
*   **语法保障**：内置的语法验证机制有效防止了智能体生成“一眼假”的无效代码。

### 8. 不足与局限
*   **作用域限制**：目前仅支持**单文件内**的 AST 解析，尚未建模跨文件的语义依赖（如继承链、跨模块调用图）。
*   **语法依赖**：要求源文件本身必须是语法正确的。如果代码库中存在已有语法错误的文件，AST 解析将失效。
*   **语言覆盖**：虽然在 CAB 中测试了多语言，但核心的修复实验（SWE-Bench）仍集中在 Python。对于静态强类型语言（如 Java/C++）中复杂的泛型或宏处理，其表现尚待进一步验证。
